# Кандидатогенерация для поиска услуг на Авито

## 1. Задача

По короткому поисковому запросу («автоподбор», «скупка телевизоров», «баня на дровах») нужно отобрать из корпуса
в 189 212 объявлений до 50 кандидатов, которые дальше уйдут на ранжирование. Метрика — Recall@50, усреднённая
по 2 452 запросам бенчмарка. Порядок внутри полусотни не важен, поэтому все 50 мест нужно заполнять всегда.

Правильный ответ — объявление, которое пользователь в итоге выбрал. Обычно оно одно: в трейне 85 % сессий
заканчиваются одним выбором.

Данные — три parquet-файла: 497 673 пары «запрос → выбранное объявление» для обучения, 2 452 неразмеченных
запроса и корпус объявлений. Несколько фактов из разведочного анализа (`eda/EDA.md`) определили почти всё
решение:

- 63 % текстов запросов бенчмарка в трейне не встречаются, поэтому подсмотреть ответ в истории нельзя;
- только 5 % объявлений трейна есть в корпусе — запоминать `item_id` бессмысленно, учиться приходится
  на текстах и категориях;
- при поиске по городу пользователь выбирает объявление из того же города в 93 % случаев;
- `search_location_id` бывает двух уровней: город и регион (или вся страна). Региональные id никогда
  не встречаются у объявлений, и в бенчмарке таких запросов 17 % против 11 % в трейне;
- фильтр «Вид услуги» совпадает с параметром выбранного объявления в 98 % случаев, но задан лишь у трети
  запросов бенчмарка.

## 2. Решения и почему

Решение — каскад: сначала гео-пул и несколько поисковых систем набирают около тысячи кандидатов, затем
градиентный бустинг выбирает из них 50.

**Гео как множитель, а не как фильтр.** Город запроса даёт вес 1, соседние города в радиусе 100 км — 0.6.
Для регионального поиска города берутся из наблюдённых выборов трейна: те, что дают первые 90 % выборов
региона, идут с весом 1, хвост — 0.8. Множитель применяется к скорам всех поисковых систем. Жёсткий фильтр
по городу отсекал бы 6.7 % правильных ответов из соседних городов, а ярусы «сначала город, потом всё
остальное» в больших городах никогда не доходили бы до соседей: пул из двадцати тысяч объявлений не
исчерпывается. Иерархия гео дала +0.026 на валидации — больше, чем любая другая детерминированная идея.

**Четыре источника кандидатов.** BM25 по стеммам (заголовок, полезные поля параметров, описание), дообученный
e5-small, USER-base и «похожие запросы трейна». Последнее — единственный коллаборативный сигнал для новых
текстов: для запроса ищутся ближайшие тексты обучающей части, и кандидат сравнивается с центром того, что
по ним выбирали. Списки складываются, потому что метрике важен состав, а не порядок: объединение поднимает
потолок кандидатов до 0.98.

**Дообучение энкодера.** Треть правильных объявлений, не попавших в кандидаты, не имеет с запросом ни одного
общего слова: «ногти» вместо маникюра, «муж на час», «вспахать» вместо вспашки. Предобученный e5 знает русский
язык, но не язык Авито. Контрастивное дообучение на 146 тыс. парах с жёсткими негативами (объявления того же
города, которые исходная модель ставит высоко, но которые никто не выбрал) подняло долю найденного на глубине
50 с 0.826 до 0.874 — выше, чем у BM25. Проверка на новых текстах показала прирост больше, чем на знакомых,
то есть модель обобщила, а не запомнила пары.

**Переранжирование бустингом.** 60 признаков: BM25 по отдельным полям и покрытие слов запроса, косинусы
обоих энкодеров и ранги в их списках, гео-множитель и расстояния, совпадение фильтров и вероятность
подкатегории, отзывы и рейтинг, история выборов. `HistGradientBoostingClassifier` из scikit-learn, поточечная
задача «выбрано / не выбрано», топ-50 по вероятности. Ранжирующие цели CatBoost (YetiRank, QuerySoftMax)
дали на 0.002 меньше, а ансамбль с ними — +0.001, то есть шум; узким местом оказалась не функция потерь,
а сигнал. LightGBM не используется намеренно: его колесо для macOS требует системную libomp, и решение
перестало бы воспроизводиться одной установкой зависимостей. Итоговая модель — среднее пяти моделей
с разными `random_state`, разброс одиночной модели около 0.0008.

**Валидация, которая знает свою погрешность.** Локальная выборка собрана так, чтобы повторять бенчмарк:
разрез по тексту запроса, стратификация по частоте текста, уровню локации, наличию фильтра и размеру
городского пула, корпус бенчмарка плюс правильные ответы отложенных запросов. Все статистики по разметке
(регион → города, запрос → подкатегория, история выборов) считаются только по обучающей части: иначе метрика
показывает то, чего на бенчмарке не будет.

Даже так локальная цифра оказалась стабильно выше платформы на 0.03–0.04. Причину видно в данных: корпус
собран вокруг запросов бенчмарка, у них в городе в полтора раза больше объявлений тех же подкатегорий, чем
у наших проверочных запросов. Полностью это не воспроизводится, зато разрыв оказался предсказуемым.
По отправкам построена калибровка (`платформа ≈ 0.913 × локально + 0.040` по шести точкам), и дальше каждая
версия отправлялась, только если прогноз проходил заранее выбранный порог. Для последней отправки прогноз был
0.912–0.914, факт — 0.9134.

**Разбор промахов.** После каждой версии потери раскладывались по типам — отсюда и брались следующие шаги
(полный разбор с цифрами по сегментам — `docs/decomposition.md`).

| Промах | Сколько | Что сделал |
|---|---|---|
| правильный ответ в кандидатах, но на местах 51–100 | 58 % промахов ранжирования | глубина кандидатов 500, точные текстовые признаки, ансамбль сидов |
| подкатегория объявления не в топ-5 предсказанных | 29 % | вероятность подкатегории как признак, предсказание по стеммам и по похожим запросам |
| другой город при городском поиске | 14 % | соседи в радиусе 100 км с весом 0.6, расстояние как признак |
| выше стоит «тёзка» — копия с тем же заголовком | 12 % | пробовали ограничивать копии в выдаче, recall падал — оставили как есть |
| правильный ответ вне гео-пула | 40 % промахов кандидатогенерации | веса вместо жёсткого фильтра, глобальный ярус после городского |
| ни одного общего слова с запросом | 32 % | дообучение энкодера на парах трейна |
| запрос с новым текстом | две трети всех потерь | похожие запросы трейна + дообученный энкодер |

Попыток было семь, содержательных решений — шесть: седьмая ушла на перегенерацию ответа детерминированным
кодом. Отклонённые гипотезы с цифрами лежат в `docs/hypotheses.md`: топонимы как буст к скору, ограничение
числа объявлений-«тёзок» в выдаче, страховка местами базового гибрида, кросс-энкодер (и готовый,
и дообученный на наших парах — он выталкивал правильные ответы чаще, чем находил), второй круг дообучения
энкодера и слияние двух версий решения.

## 3. Метрика

**Recall@50 на бенчмарке — 0.9134.** На локальной валидации 0.9525.

| Отправка | Что добавилось | Локально | Платформа |
|---|---|---|---|
| 1 | BM25 в гео-пуле + e5-small | 0.8665 | 0.8356 |
| 2 | иерархия гео: соседние города, ядро региона | 0.8920 | 0.8514 |
| 3 | переранжирование бустингом | 0.9225 | 0.8796 |
| 4 | глубина кандидатов 500, признаки покрытия и гео для регионов | 0.9308 | 0.8840 |
| 5 | USER-base, похожие запросы, дообученный e5 | 0.9464 | 0.9081 |
| 6 | история по запросу, дешёвые признаки, ансамбль пяти сидов | 0.9525 | **0.9134** |
| 7 | то же решение, перегенерировано детерминированным кодом | 0.9525 | **0.9134** |

Для ориентира: BM25 без гео даёт 0.456, гео без текста (популярность объявления) — 0.060, а правильный ответ
вообще попадает в кандидаты в 0.980 случаев. То есть из 0.98 достижимого переранжирование забирает 0.95;
больше половины оставшихся промахов стоят на местах 51–100, то есть проигрывают буквально чуть-чуть.

## Как запустить

Нужны сырые файлы задачи в `dataset/` (`train_pairs.parquet`, `benchmark_queries.parquet`,
`benchmark_items.parquet`) и Python 3.11+.

```bash
pip install -r requirements.txt
```

**Быстрый путь — из готовых артефактов (~15 минут).** Скачать `artifacts.tar.gz`
([Яндекс.Диск](https://disk.yandex.ru/d/rNbgW7DxYU6e-w), 352 МБ, md5 `004b2e9c6ecc24b4aefea081a8e72d9e`)
и распаковать в корень проекта: `tar -xzf artifacts.tar.gz`. Внутри дообученный энкодер
`data/models/e5-small-ft` и ансамбль переранжирования `data/rerank/model_rr_all_ens5_v5.joblib`. Дальше:

```bash
python -m src.build_dataset                                   # data/processed из сырых parquet, ~5 минут
python -m src.rerank.predict --model rr_all_ens5 --out answer.csv
python -m src.submission answer.csv                           # проверка формата
```

Первый прогон дополнительно закодирует корпус двумя энкодерами (~40 минут на M1, результат кэшируется
в `data/embeddings`).

**Полный путь — с нуля (~4 часа на M1):** `scripts/reproduce.sh`. Он делает то же плюс нарезку валидации,
дообучение энкодера и обучение пяти моделей ансамбля.

Веса исходных энкодеров (`intfloat/multilingual-e5-small`, `deepvk/USER-base`) скачиваются с HuggingFace
при первом запуске. Всё считалось на MacBook Pro M1 с 32 ГБ памяти, без GPU.

### Про воспроизводимость

`answer.csv` в корне — тот самый файл, который загружен на платформу. `src.rerank.predict` с теми же
артефактами выдаёт его побитово: два контрольных прогона подряд дали одинаковый md5.

Ради этого пришлось починить одно место. Вероятности подкатегорий копились обходом `set` строк, а порядок
обхода зависит от хеша, который Python рандомизирует на каждый процесс. Складывались одни и те же числа
в разном порядке — расходились последние биты float, и близкие кандидаты изредка менялись местами.
На метрику это не влияло (расхождение было в одном запросе из 2452), но воспроизводимость ломало.
Теперь стеммы обходятся отсортированными.

## Что где лежит

| Путь | Что там |
|---|---|
| `src/features/` | нормализация и стемминг текста, парсер параметров, гео, топонимы, предсказание подкатегории |
| `src/retrieval/` | BM25, обёртка над энкодерами, гео-пулы с весами, базовый гибрид |
| `src/rerank/` | признаки кандидатов, история похожих запросов, обучение и предсказание |
| `src/finetune/` | контрастивное дообучение энкодера |
| `src/validation.py` | нарезка локальных сплитов под распределение бенчмарка |
| `docs/hypotheses.md` | журнал всех гипотез: описание → эксперимент → результаты → решение |
| `docs/decomposition.md` | разбор потерь recall по сегментам и типам промахов |
| `eda/EDA.md` | разведочный анализ данных |
| `tests/` | тесты метрики, формата ответа и сборки признаков истории |
